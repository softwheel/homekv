## V1 — Shard mapping compatibility

Verify:

- `ShardId::new(0)` and `ShardId::new(1023)` succeed;
- `ShardId::new(1024)` fails;
- checked-in raw-byte keys map to fixed golden shard IDs;
- property test over many generated byte strings always returns `< 1024`;
- mapping is deterministic across repeated calls and independent of node/membership objects.

Changing a golden result is a compatibility change, not a test update.

## V2 — Candidate A state-machine semantics

Use a simple reference `HashMap` model and generated deterministic command sequences. Compare after every command:

- absent/present GET;
- insert;
- overwrite smaller/larger value;
- delete present/absent;
- repeated idempotent PUT/DELETE;
- single-shard batches with repeated keys.

The engine's visible state and metrics must agree with the reference model.

## V3 — Atomic batch visibility

Construct a batch that changes several correlated keys between two recognizable states. Run concurrent GET observers while repeatedly applying whole batches.

For Candidate A every observed multi-key test snapshot/history must be explainable as either the complete pre-state or complete post-state at operation boundaries. No history may require a partially applied batch.

Because individual GET RPCs are separate operations, tests that require a multi-key atomic observation must use an owner-side test/query hook or recorded operation history rather than incorrectly assuming two independent GET calls form one snapshot.

Candidate B, if implemented, additionally requires sequence/version concurrency/model tests proving direct GET cannot accept a value from an in-progress batch.

## V4 — Queue and cancellation

With a tiny queue capacity and a deliberately paused/controlled owner:

- fill the queue and prove `try_*` returns `QueueFull`;
- verify queue storage never exceeds configured capacity;
- cancel a future before successful admission and prove it is not applied;
- drop a response receiver after successful admission and prove the accepted mutation is still applied exactly once in owner order;
- close/shutdown and prove new admission returns `Closed`;
- prove accepted work drains before explicit shutdown completes.

## V5 — Memory accounting

Table tests must cover:

1. insert new key/value;
2. replace with same-size value;
3. replace with smaller value;
4. replace with larger value;
5. delete present key;
6. delete absent key;
7. batch containing multiple keys;
8. batch touching the same key more than once.

After each case:

```text
logical_bytes == sum(key.len + value.len for every resident entry)
key_count == number of resident entries
```

M1 benchmark memory evidence separately records process RSS delta/bytes-key and labels it approximate exactly as M0 did.

## V6 — No whole-dataset mutation copy

Proof combines:

- source review: Candidate A mutates its owned map in place and contains no `HashMap::clone`/full snapshot on PUT/DELETE;
- benchmark scaling: compare 1k/10k/50k mutation p50 and throughput;
- optional allocation/profiling evidence where practical.

Mandatory gate:

- 50k/1k PUT p50 ratio <= 4.0;
- 50k PUT p50 and throughput each improve >=10x versus verified M0 engineering medians, unless requirements are amended before verification.

## V7 — Repeated M1 benchmark

Capture at least three complete Candidate A repetitions against one exact commit.

Primary cells:

- 16B key / 64B value
- 1k / 10k / 50k keys
- GET / SET / DELETE / 80% GET + 20% SET
- >=10,000 measured operations/cell unless explicitly documented
- deterministic seed
- throughput + p50/p95/p99 + sample count
- host/toolchain metadata

Report median and run spread. Never select only the fastest repetition.

The M1 summary must include the verified M0 values/ratios without modifying or recapturing M0.

## V8 — Existing API integration

After the migration adapter lands, exercise the current public HomeKV GET/SET/DELETE path against Candidate A:

- existing request/response semantics remain unchanged;
- server tests pass;
- no new M2 wire protocol is introduced;
- failures due to bounded overload/closed shard are explicit rather than silently dropped.

## V9 — Crossbeam promotion, if attempted

Candidate B requires all mandatory correctness gates plus the numeric promotion rule from `requirements.md`.

The verification handoff must contain one of:

- **Promoted** — every promotion criterion is evidenced and Candidate B becomes primary; or
- **Not promoted** — Candidate A remains primary and the Crossbeam results/limitations are retained.

Failure to promote Candidate B does not fail M1 when Candidate A satisfies all mandatory M1 gates.
